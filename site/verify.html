Get the image

Verify

Every published image is signed by digest with one key and attested by the run that built it. A migrated host repeats the signature check on every pull.

From any machine

The key is cosign.pub in the repository, the same file the image installs as /etc/pki/containers/matrixdj96.pub. The signature sits on the digest, so it holds whichever tag you name. Each release run also records a build provenance attestation in GitHub's store, tied to this repository and to the digest it built.

cosign verify --key https://raw.githubusercontent.com/MatrixDJ96/bazzite-mx/main/cosign.pub \
  ghcr.io/matrixdj96/bazzite-mx:stable

gh attestation verify oci://ghcr.io/matrixdj96/bazzite-mx:stable --repo MatrixDJ96/bazzite-mx

Name another image or a dated tag to check that one. gh attestation verify wants a GitHub login first (gh auth login, or GH_TOKEN in the environment), public repository or not.

The SBOM

The packages of each image are listed in a syft JSON document, attached to the image as a referrer under the type application/vnd.spdx+json and signed with the same key. The release notes print the diff between two releases; the document itself is two oras calls away: discover for its digest, pull of that digest for the file. The image does not carry oras: the repo's .github/scripts/install-oras.sh <version> <dir> installs it into a directory of your choice, at the version the workflows set in ORAS_VERSION.

digest=$(oras discover --format json ghcr.io/matrixdj96/bazzite-mx:stable \
  | jq -r '.referrers[] | select(.artifactType == "application/vnd.spdx+json") | .digest')
oras pull --output sbom "ghcr.io/matrixdj96/bazzite-mx@$digest"

What the host verifies

After ujust migrate the origin is ostree-image-signed:docker://ghcr.io/matrixdj96/<image>:stable. The image's /etc/containers/policy.json carries the ghcr.io/matrixdj96 scope as sigstoreSigned with the key above, and keeps default on reject. That default covers no container pull: containers-common leaves the empty docker scope on insecureAcceptAnything, so a pull is verified only under a scope the policy names: ours, and the ones Bazzite ships (ghcr.io/ublue-os, quay.io/toolbx-images, the two Red Hat registries). The tag stays free while the signature is checked on the digest, and a failing pull is refused before anything is staged.

ujust verify-host checks the policy in force (install). A local copy of policy.json shadows the image's, which is why the migration recipe offers to restore it first.

How a release is gated

A push never publishes. A release is a dispatched run: by hand, by the weekly trigger, or by the watcher that compares the base's digest with the one the current :stable was built from.

Build and stage

The run builds the three images, probes each one, pushes it to :staging, signs it and records the attestation.

Gate and tag

A separate job verifies all of that again by digest, with two negative controls. Only then does the run write the dated tag; :stable moves only when the dispatch asks for it and the repository's PROMOTE_STABLE variable allows it.
