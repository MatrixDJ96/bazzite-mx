FAQ

The questions a first rebase raises.

Is this Bazzite?

It is built on Bazzite's images and follows their stable stream. It stays a personal image with one maintainer, public and usable at your own risk. Bazzite's documentation covers everything it does not change, and what changes lists what it does. Its rollback helper is the exception: brh rebase <tag> looks for this image under ghcr.io/ublue-os/, where it does not exist, so a dated release is reached with ujust migrate apply <tag> (tags).

Which image is mine?

bazzite-mx for AMD or Intel graphics, bazzite-mx-nvidia-open for an NVIDIA GPU the open kernel modules cover (Turing and newer), bazzite-mx-nvidia for Maxwell, Pascal and Volta (/usr/share/doc/nvidia-driver/supported-gpus.json in each NVIDIA image). A GPU older than Maxwell has no NVIDIA flavour, nor has one passed to a virtual machine: that host stays on bazzite-mx, and ujust verify-host keeps failing its flavour line. lspci -d 10de: says whether there is an NVIDIA GPU.

Why does the first rebase go through the unsigned transport?

A signed pull is checked against the policy of the deployment that runs it, and stock Bazzite carries no trust for ghcr.io/matrixdj96. After that one pull, the policy inside the image checks every later pull (verify).

What happens to the packages I layered on Bazzite?

ujust migrate apply removes them all after naming them and asking (ujust migrate alone is the read-only plan), because bootc marks a deployment incompatible on any rpm-ostree group. What you need on top goes to Flatpak, Homebrew or a distrobox; what needs the image layer is a change to the image.

Why are the Firefox and virt-manager Flatpaks denied?

Both are RPMs in the image, so a Flatpak would be a second copy one click away in Discover. The Firefox profile is copied by hand (install).

I have an MSI laptop and the modules do not load.

msi-ec and acpi_ec are unsigned, so the kernel refuses them while Secure Boot is on, where stock Bazzite loads its own signed msi-ec. Check bootctl status; with Secure Boot off, ujust setup-msi enable loads them and installs MControlCenter.

ntfs3, ntfs or ntfs-3g: which driver mounts my NTFS volumes?

ntfs3 by default, and ujust migrate rewrites fstab rows onto it. The type ntfs is the NTFSPLUS driver, used only after ujust setup-ntfsplus enable. ntfs-3g is the FUSE driver and stays available as an explicit type. On a host that did not opt in, mount -t ntfs fails with an unknown filesystem type instead of landing on FUSE. A volume the file manager mounts takes ntfs3, or NTFSPLUS after the opt-in, where Bazzite takes ntfs-3g.

How do I go back?

rpm-ostree rollback && systemctl reboot boots the previous deployment again; the migration recipe pinned it, so it survives garbage collection until you unpin it. After a second ujust migrate apply before the unpin, two deployments can be pinned and the one from before the migration is the older, which rpm-ostree rollback does not reach: pick it in the boot menu, which lists the deployments in rpm-ostree status order. Unpin every deployment that ostree admin status marks Pinned: yes with sudo ostree admin pin -u <index>, the index being its position in that list, counted from 0. To leave the image, first run ujust setup-ntfsplus disable and ujust setup-msi disable if you enabled them, then sudo rpm-ostree rebase ostree-image-signed:docker://ghcr.io/ublue-os/<image>:stable, <image> being bazzite, bazzite-nvidia-open or bazzite-nvidia.

Can I build it myself?

Yes: podman build with BASE_IMAGE and IMAGE_NAME as build arguments. The build runs the smoke tests and ends with bootc container lint --fatal-warnings (the repository).

Something is wrong. Where do I say so?

In the repository's issues, with the output of ujust verify-host and, for a pull, of rpm-ostree status.
