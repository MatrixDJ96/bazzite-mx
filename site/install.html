Install

A Bazzite host reaches the signed origin through ujust migrate. A host already on the image is re-checked with ujust verify-host, which names every defect and the recipe that fixes it.

  • A Bazzite host that has never run the image
  • A host already on the image

A Bazzite host that has never run the image

Four steps and two reboots. Pick the image for your GPU first (images).

  1. Rebase once through the unsigned transport.

    Stock Bazzite trusts no key for ghcr.io/matrixdj96, so the first pull cannot be verified. On an NVIDIA machine name bazzite-mx-nvidia-open (Turing and newer) or bazzite-mx-nvidia (Maxwell, Pascal and Volta) instead; an older GPU stays on bazzite-mx.

    An ntfs row of fstab is ntfs-3g on Bazzite; the image has no mount.ntfs and blacklists the driver, so its first boot fails such a row, and one without nofail stops that boot in emergency mode (the previous deployment in the boot menu still boots: fix the rows there and run the rebase again). Before the rebase, take out of those rows any option only ntfs-3g reads (big_writes, locale=, remove_hiberfile), which ntfs3 refuses, then switch them to ntfs3 or give them nofail.

    sudo rpm-ostree rebase ostree-unverified-registry:ghcr.io/matrixdj96/bazzite-mx:stable

    This pull fetches only the layers the host lacks; step 5 of the migration rebases onto the same tag through the signed transport, and downloads nothing new unless :stable moved in between. The image's base can be days behind Bazzite stable, so the rebase may print a Diff: with downgraded packages and an older kernel: expected, the next release moves the base forward.

    The rebase keeps whatever the host had layered; step 3 of the migration removes it. When it fails on a local package the image also ships, rerun it dropping that request in the same transaction, <image> being the image you named above:

    rpm-ostree status --json | jq '.deployments[0]["requested-local-packages"]'
sudo rpm-ostree rebase --uninstall=<name>-<version>-<release>.<arch> \
    ostree-unverified-registry:ghcr.io/matrixdj96/<image>:stable

  2. Reboot into the new deployment.

    systemctl reboot

  3. Run the migration from a terminal.

    Step 2 runs without asking; every other step that changes the host asks first. Without a terminal nothing is confirmed: steps 0, 6 and 6b are skipped, and the run stops at the first of steps 3, 4 and 5 that asks, the pin of step 2 left in place, and a second apply before the unpin can leave two deployments pinned. plan is read-only and the default.

    ujust migrate           # plan
ujust migrate apply     # every change but step 2 asks first

    Both print what they found, then stop on a pending deployment; apply first offers step 0, and a restore confirmed there stays when the run then stops. They also stop on a booted image whose policy has no ghcr.io/matrixdj96 scope, an image older than its signing policy, and print the unsigned rebase to run again. A local policy.json shadowing the image's is named in that abort instead, and apply offers to restore it. Then the steps, each skipped when already done. There is no step 1: it is the scope precondition, checked between 0 and 2.

    StepWhat it does
    0 restores policy.json and registries.d from the image, backup kept
    2 backs up the status and fstab, pins the booted deployment, stops uupd.timer for the run; apply refuses to start while an update runs or waits to restart after a failure
    3 rpm-ostree uninstall --all, packages named first: layered, local and inactive requests alike
    4 rpm-ostree initramfs --disable, so the image's initramfs boots
    5 rpm-ostree rebase onto ostree-image-signed:docker://ghcr.io/matrixdj96/<image>:stable
    6 rewrites the ntfs rows of fstab to ntfs3, the type column switched and errors=remount-ro dropped where present, after proving the driver loadable
    6b moves leftover ntfsplus files and a host's own modules-load file for msi-ec or acpi_ec into the backup, and deletes ntfsplus kernel arguments
    7 prints what stays with each user, then rpm-ostree status

    Declining step 3, 4 or 5 aborts the run; declining 6 or 6b only skips it. Step 6 is skipped on a host that opted into NTFSPLUS. The three rpm-ostree steps land in one pending deployment.

  4. Reboot, then check the host.

    Every line is OK:, SKIP: or INFO:, or a FAIL: that names its fix or why a check could not run.

    systemctl reboot
ujust verify-host

What stays with you

Nothing is uninstalled from Flatpak. The Firefox RPM reads ~/.mozilla when it exists, ~/.config/mozilla otherwise, and the Flatpak keeps either tree in ~/.var/app, so copy it before the first RPM start. Teams is a Flatpak you install yourself.

[ -e ~/.mozilla ] || [ ! -d ~/.var/app/org.mozilla.firefox/.mozilla ] \
    || cp -a ~/.var/app/org.mozilla.firefox/.mozilla ~/
[ -e ~/.config/mozilla ] || [ ! -d ~/.var/app/org.mozilla.firefox/config/mozilla ] \
    || cp -a ~/.var/app/org.mozilla.firefox/config/mozilla ~/.config/
flatpak uninstall org.mozilla.firefox          # when you are done with it
flatpak install flathub com.github.IsmaelMartinez.teams_for_linux

Rollback at any point before the unpin: rpm-ostree rollback && systemctl reboot boots the previous deployment; after a second apply the one from before the migration is the older of the two pinned, which rpm-ostree rollback does not reach: pick it in the boot menu, which lists the deployments in rpm-ostree status order. After a day of use, unpin every deployment that ostree admin status marks Pinned: yes with sudo ostree admin pin -u <index>, the index being its position in that list, counted from 0. A second ujust migrate on the migrated host prints nothing to do.

A host already on the image

ujust verify-host is the whole procedure: one OK:, FAIL:, SKIP: or INFO: line per check, exit 1 on any FAIL:. The lines a host is most likely to see:

FAIL lineFix
bootc status reports the booted deployment incompatible ujust migrate: an rpm-ostree group is left in the origin
origin is not ostree-image-signed:... ujust migrate apply
origin tag is X, not stable ujust migrate apply stable: a dated tag never updates
rpm-ostree mutations in the origin: ... ujust migrate; an override: sudo rpm-ostree override reset --all
policy.json has no sigstoreSigned scope sudo ostree admin config-diff, then ujust migrate apply
MSI host: msi_ec not loaded ujust setup-msi enable
NVIDIA GPU present but the image is bazzite-mx sudo rpm-ostree rebase ostree-image-signed:docker://ghcr.io/matrixdj96/bazzite-mx-nvidia-open:stable, or bazzite-mx-nvidia for Maxwell, Pascal and Volta; that one boots another kernel series, so with the NTFSPLUS opt-in active run ujust setup-ntfsplus disable before the rebase and enable after the reboot. A GPU older than Maxwell, or one passed to a virtual machine, stays on bazzite-mx and keeps this line
fstab: <target> uses type ntfs without the ntfsplus opt-in ujust migrate for ntfs3, or ujust setup-ntfsplus enable; the volume mounts at the next boot or with sudo mount <target>
fstab: <target> is ntfs without errors=remount-ro ujust setup-ntfsplus enable adds the option, which mounts a dirty or hibernated volume read-only
fstab: <target> is <type> but not mounted on ntfs3 a dirty NTFS volume is the usual reason: a full shutdown on Windows, or sudo ntfsfix -d <device>, the device being the row's source (findfs UUID=<uuid> prints it); on ntfs, journalctl -b | grep ntfs names the option NTFSPLUS refused, or the driver missing or refused with Secure Boot on (ujust setup-ntfsplus enable says why)
fstab: <target> is <type> but its device <source> is absent an unplugged volume whose row lacks nofail: plug it in, or add nofail

The complete map, one row per line, is in docs/migration.md. An INFO: line is not a failure: the Firefox Flatpak still installed, the ntfs driver not registered yet, fstab rows left on ntfs-3g, a nofail volume whose device is absent, a noauto volume not mounted.
